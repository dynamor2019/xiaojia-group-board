# 技术原理

这份文档记录两件事：**数据是怎么拿到的**，以及**为什么这么拿不会把号跑封**。
踩过的坑都写在里面，省得你再踩一遍。

> 文中提到的文件位置：代码都在 `app/`，运行时产物都在 `data/`
> （`data/群公告_*.json`、`data/微信群公告_*.json`、`data/board_state.json`、`data/data_store.json`、`data/logs/`），
> 解密产物在 `app/vendor/wcdb-key-tool/decrypted/`。

---

## 一、QQ 侧

### 1.0 NapCat 是怎么来的

NapCat 是第三方项目，不在本仓库里。早期版本让用户自己去 Releases 页面挑包，这一步
劝退了不少人 —— 四个 zip 名字长得几乎一样，选错就白下 100 MB。现在改成 `app/napcat_setup.py`
自己去 GitHub API 查最新 release 并解压，原因很简单：**其中只有一个包能自动化**。

| 包 | 大小 | 能不能脚本化 |
|---|---|---|
| `NapCat.Framework.zip` | 35 MB | 不能，给 Linux/macOS |
| **`NapCat.Shell.zip`** | **34 MB** | **能 —— 解压即用，目录就是最终形态** |
| `NapCat.Shell.Windows.Node.zip` | 118 MB | 能，但自带 Node 运行时，本机有 node 就纯浪费 |
| `NapCat.Shell.Windows.OneKey.zip` | 1 MB | 不能，里面是 `NapCatInstaller.exe`，要人点向导 |

所以代码只认 `NapCat.Shell.zip`：解开后 `NapCatWinBootMain.exe` / `NapCatWinBootHook.dll` /
`napcat.mjs` / `qqnt.json` / `loadNapCat.js` 五个文件必须在，缺一个就判定失败，
避免把半截目录交给后面流程。这条 `REQUIRED` 校验也是判断"装没装"的唯一标准。

解压时有一条特殊规则：**`config/` 下已存在的文件不覆盖**。因为
`config/napcat_<QQ号>.json` 存着登录态，覆盖就等于让人重新扫一次码。这样"重新点一次下载"
可以安全地当升级用。

写入边界只有一处：配置里的 `napcat_dir`（默认 `<项目根>/napcat`）。不碰 QQ 安装目录、
不碰注册表、不需要管理员权限。

### 1.1 为什么要"抓完就跑"

NapCat 的工作方式是把自己作为一个 Node 插件**注入到 QQ 进程里**，然后对外暴露一个
OneBot 协议端点。问题在于注入时机：它只能挂到**新创建**的 QQ 进程上。

如果你的 QQ 已经开着，`auto.py` 是注不进去的 —— 这不是 bug，是机制决定的。
所以整个流程被设计成：

```
检测 QQ 是否已开
  ├─ 已开  → 直接放弃 QQ 这条路（不硬来，不杀你的进程）
  └─ 没开  → 用 NapCat 的快速登录拉起 QQ
              ↓
        等 OneBot 端点就绪（反向 WS 连上来）
              ↓
        get_group_list → 逐群 get_group_msg_history，只读
              ↓
        抓完 → 立刻退出这个 QQ 进程
```

退出这一步很重要：跑完之后机器的状态回到"你平时手动登录 QQ"的样子，
不会留下一个常驻的、被动过手脚的客户端。

**关于扫码**：拉起 QQ 的命令是 `NapCatWinBootMain.exe QQ.exe <inject.dll> -q <QQ号>`，
`-q` 就是快速登录 —— 它不重新走一遍密码/扫码流程，而是复用本机已有的登录态
（NapCat 首次登录成功后会写一份 `config/napcat_<QQ号>.json`，有这个文件基本就代表登录态还在）。

所以：

- 登录态有效 → 静默拉起，**不用扫码**
- 登录态失效 / 首次 / 换号 → QQ 会要求登录，**扫一次**，之后长期免扫

`crawl_ws.py` 侧给 NapCat 的连接等待上限是 **120 秒**，加上拉起后的 8 秒固定等待，
实际留给人扫码的窗口约两分钟。超时会打印「等了 120 秒 NapCat 仍未连接」，
并且 `auto.py` 会把这次拉起的 QQ 整棵树收掉，不留残留。

### 1.2 消息怎么取

`crawl_ws.py` 起一个本地 WebSocket server，NapCat 反向连过来（所以不需要向任何端口发请求，
也绕开了 3000 端口被系统保留的问题）。

一次完整的抓取：

1. `get_group_list` —— 拿群列表，先剔掉已退订的群（`board_state.json` 里的 `muted`）
2. 对每个群 `get_group_msg_history`，每页 100 条
3. 只认 `message[].type == "at"` 里 `qq` 为 `all` 的消息 —— 也就是 `@所有人`
4. **增量策略**：新消息在前，一旦翻到比上次记录更旧的消息就停，不再往下翻
5. 结果合并进累计库 `data_store.json`，按 `群名` 分组

首次运行（没有累计库）或加 `--full` 时才回溯完整时间窗口。

### 1.3 缓存与幂等

`data_store.json` 是滚动累计的，按 `(time, sender, text)` 去重。
重跑不会产生重复条目，也不会丢历史 —— 这让"每天跑一次"变得安全，
哪怕某天因为 QQ 已开着跳过了一次，第二天照样补齐。

### 1.4 为什么 NapCat 跟着 QQ 版本走

NapCat 不是协议库，它**不自己实现 QQ 协议**，而是把自己塞进 QQ 进程里当"内部中间件"。
具体做法是替换启动入口：`NapCatWinBootMain.exe` 拉起 QQ 之后，由 `loadNapCat.js`
把 NapCat 的模块挂进去，之后 OneBot 收到的事件其实来自 QQ 自己的网络层。

这决定了它是**版本敏感**的，而不是插件的错：

```
QQ 目录结构：QQNT\versions\<版本号>\resources\app\package.json
                 ↑ NapCat 启动时会去这里读版本号，来决定用哪套注入姿势
```

所以 QQ 每次大版本更新（改了 `resources/app` 的目录布局或主进程入口），
NapCat 就得跟着适配一版。实测门槛是 **QQNT ≥ 9.9.27（构建 40768+）**，
低于这个数直接起不来；高于 NapCat 适配的版本，通常表现是能启动但登录卡住、
或者 `get_group_list` 返回空 —— 也就是"跑完了，一条都没抓到"。

`doctor()` 里加了一行 `QQ 版本`：读 `versions/config.json` 的 `curVersion`，
低于 40768 标黄。这里刻意**只报下限、不报上限** —— 上限是 NapCat 的作者在追，
写死在代码里只会天天误报（本机 QQ 9.9.36 配 NapCat 4.18.41 就正常，
但它的 `qqnt.json` 里写的还是 9.9.22）。

### 1.5 风控是怎么被触发的

必须承认：**这套流程有账号风险，而且真实发生过**。原因不在"改客户端"，
而在**登录行为的形状**：

| 行为 | 在腾讯眼里像什么 |
|---|---|
| 每天定时启动 QQ → 登录 → 抓完退出 | 一个从不用手机、只在固定时刻上线几分钟的账号 |
| 换一台电脑继续跑 | 同一账号短时间内异地/异机登录 |
| 一天跑很多次 | 反复登录退出，典型的脚本特征 |
| QQ 刚被限制完立刻又跑 | 二次触发，判定会加重 |

微信侧没有这个问题，因为它**不登录、不注入**，只是读磁盘上的库（只读内存取密钥）。
QQ 侧做不到 —— 消息只能从活着的进程里问出来，而要问就得先登录。

所以文档里给的建议都是"降低行为异常度"而不是"技术手段规避"：
一个号固定一台机器、一天一次、被抓完就关、换环境先养几天。
真被限制了，走官方验证 / 客服申诉，别指望工具能替你解开。

## 二、微信侧

这是整个项目技术含量最高的部分，也是最容易被想歪的部分。

### 2.1 数据在哪

微信 4.x 的数据目录长这样（真实路径由 `%APPDATA%\Tencent\xwechat\config\*.ini`
里的那行字符串指定，可以整个挪到别的盘）：

```
xwechat_files/
└─ wxid_xxxxxxxx_1234/
   └─ db_storage/
      ├─ contact/contact.db        联系人、群名、备注
      ├─ message/message_0.db      消息，按会话分表
      ├─ message/message_1.db      分片
      ├─ session/session.db        会话列表
      └─ ...
```

**群消息在 `message_N.db` 里，表名是 `Msg_<md5(群ID)>`。** 群 ID 形如 `123456789@chatroom`，
所以你得先算出 md5 才能定位到表 —— 这是第一个坑。

行结构的关键字段：

| 字段 | 含义 |
|---|---|
| `local_type` | `1` = 文本；其他是图片/语音/引用等 |
| `message_content` | 文本内容，`"wxid_发送者:\n正文"` |
| `WCDB_CT_message_content` | 压缩标记，`4` 表示这列是 zstd 压缩的（文本不走） |
| `real_sender_id` | 指向 `Name2Id` 表的 rowid，用来还原发送者 |
| `create_time` | Unix 秒 |

所以取一条 `@所有人` 的流程是：`Msg_<md5>` 表 → 过滤 `local_type=1` →
`message_content LIKE '%@所有人%'` → 按 `real_sender_id` 关联 `Name2Id` 拿 wxid →
再拿 wxid 去 `contact` 表查 `remark` / `nick_name` 显示名。

### 2.2 库是加密的（SQLCipher 4）

`db_storage` 下的 `.db` 全是 SQLCipher 4 加密的：

- 算法：AES-256-CBC + HMAC-SHA512
- 页大小 `4096`，每页尾部保留 `80` 字节 = `IV(16) + HMAC(64)`
- 第 1 页结构：`[salt 16][密文 4000][IV 16][HMAC 64]`
- 每个库的 salt 独立，所以**每库一把独立派生密钥**

HMAC 校验时页码是**小端序**（`struct.pack('<I', 1)`）—— 这是第二个坑，
按大端写会全部校验失败。

### 2.3 为什么老工具在微信 4.1+ 全部失效

以前大家都是"扫进程内存找 `x'<64位十六进制key><32位salt>'`"这个模式。
微信 4.1.10 之后这条路被彻底堵死：

> 进程内存里不再缓存算好的明文密钥，只剩一个 passphrase。
> 真正的密钥要用 PBKDF2-HMAC-SHA512、**256000 轮**现算现用，算完就丢。

所以扫描 2GB 内存得到 **0 命中** 不是工具写错了，是设计上就没有了。
这也是为什么这个项目直接 vendor 了
[wcdb-key-tool](https://github.com/TANGandXUE/wcdb-key-tool) 而不是自己硬写。

### 2.4 现在的取密钥方式

思路是"不猜，跟着微信自己的代码走"：

```
在内存里找 com.Tencent.WCDB.Config.Cipher 这个字符串字面量（锚点）
  → 顺着引用找到持有它的对象
  → 读出那段结构，用固定 27 字节掩码 XOR 还原
  → 从还原结果里读出 x'<passphrase><salt>'
  → PBKDF2-HMAC-SHA512(passphrase, salt, 256000) 派生 32 字节密钥
  → 用第 1 页的 HMAC 验证（对得上才认）
```

实测：24 个库 / 12 秒 / 24 个全部通过 HMAC 校验。

**安全边界**，逐条说明：

- 只用 `OpenProcess(PROCESS_VM_READ)` + `ReadProcessMemory`，**只读**
- 不 `WriteProcessMemory`，不 `CreateRemoteThread`，不注入 DLL，不挂调试器
- 不改微信安装目录、不改配置、不动登录态
- 不联网，一个包都不发

换句话说，它做的事和你用 Process Explorer 看一眼微信内存没有本质区别，
只是它看得更准、并且能算。

### 2.5 解密与查询

拿到密钥后：

```python
# 每页解密后，把尾部 80 字节替换成 0，其余保留
# 第 1 页特殊：把 [salt 16] 换回 "SQLite format 3\0"
plain = aes256cbc_decrypt(key, page[:4096-80])
```

产物写到 `decrypted/`，是**可以直接用 sqlite3 打开**的普通数据库。
之后所有查询都是标准 SQL，跟加密无关了。

解密只读原库，不动 `db_storage` 里的任何文件。

### 2.6 为什么微信不用退出

因为整个链路是 **磁盘 → 解密 → 查询**，全程不需要微信配合。
微信在跑的时候文件会有 WAL 尾巴，但主库本身是一致的，读出来最多差最后几条，
下次跑自然补上。

这一点和 QQ 形成了鲜明对比：QQ 的数据在游戏进程的内存里，微信的数据在文件里。
所以一个必须"抓完即退"，一个可以永久常驻。

## 三、跨通道设计

### 3.1 统一的数据形状

两个通道最终写出**同一种结构**的 JSON，所以下游只有一套代码：

```json
{
  "群名 (群ID)": [
    { "time": "2026-10-29 09:12", "sender": "辅导员-王老师", "text": "@所有人 请于…" }
  ]
}
```

- QQ → `群公告_<日期>.json`
- 微信 → `微信群公告_<日期>.json`

`report.py` 读它们，给每行打上 `src` 标签（`QQ` / `微信`），然后按 `src` 分成两列渲染。

### 3.2 稳定 ID：为什么"已完成"会莫名其妙失效

看板用一条哈希当每行的 ID：

```
sha1(src | gid | time | sender | text[:40])[:12]
```

**只取不会随重跑变化的字段**。这里有个血泪教训：早期版本把 `topic`（自动生成的话题归类）
也算进了种子里，结果每次重跑规则微调一下话题，所有 ID 全变，用户之前点的"已完成"就
集体失联 —— 表现就是"标记完成后刷新又出现了"。

同理，`days` 窗口、过期判断这些也不能进种子。

### 3.3 状态为什么不能只放 localStorage

`present_files` 之类的预览面板，每次给你的是一个
`http://127.0.0.1:<随机端口>/static-html/<hash>/` 地址。
**端口变了，origin 就变了，localStorage 就是另一个世界。** 于是"点了完成、刷新又回来了"。

所以状态走三层：

1. 看板服务在跑 → POST 到 `/api/state`，写进 `board_state.json`（最可靠）
2. 没有服务 → 写 localStorage **和** cookie（cookie 用 `path=/`，跨端口共享）
3. 读的时候分两种情况：**服务在跑就只信 `board_state.json`**；没有服务才取
   localStorage ∪ cookie 的并集

第 3 条早期是"一律取并集"，结果「重置已完成」会失效：文件里清空了，本机还留着旧 ID，
一合并又回来了，标过的条目反而一直显示成划掉。所以现在服务优先时不碰浏览器存储。

界面上有个小标签实时告诉你当前处于哪一档，
如果是"仅本浏览器有效"，就说明该用 `启动看板.cmd` 了。

**界面偏好同理，但默认值要选对**

「隐藏已完成」「只看带日期的」这两个勾选框也走 localStorage ∪ cookie
（同一个 `path=/` 的 cookie，换端口不丢）。这里有个比存储更重要的原则：

> **默认值必须等于用户想要的稳态。**

「隐藏已完成」一开始默认不勾，于是每次刷新都要手动点一次 —— 而用户标记完成之后
本来就不想再看见它。改成默认勾上之后，这个开关基本不用碰了，存不存都不太要紧
（现在也存了）。反过来，如果某个默认值是"每天都要改回来"的，那不是用户的问题。

顺带一个坑：这个复选框原本还参与"群卡片默认展开"的判断
（`qs.length || onlyTodo.checked || gsel.value || hideDone.checked`）。
默认变 `true` 之后，所有卡片都会默认展开，页面长得没法看 —— 所以把它从那个条件里删掉了。
**改默认值的时候，要把它参与过的每个判断都过一遍。**

**标记完成之后，为什么刷新就看不见了**

`report.collect()` 算在稳定 ID 之后、组装之前，多了一步筛：

```python
done_ids = set(board_state.load().get("done") or [])
rows = [r for r in rows if r["i"] not in done_ids]   # 顺手数出 dropped_done
```

所以标记过的条目**根本不进 HTML**，不是靠 CSS 藏起来——`DATA` 里没有它，搜索、筛选、
统计都碰不到它，体积也跟着变小（本机实测 88 KB → 83 KB，14 条收起来了）。
页头那句"14 条已标记完成，17 条已过期，……，已隐藏"里的第一个数就是它。

两个副作用要留意：

- 统计格里的「已完成」改成读 `done.size`，因为 `DATA` 里已经没有这些行了，遍历不出来了
- 点「重置已完成」清空后，要**再点一次「刷新数据」**它们才会回来（当前页的 `DATA` 是死的）

### 3.4 退订群为什么要在爬虫侧生效

点 `✕` 不只是界面上 `display:none`，它写进 `board_state.json` 的 `muted` 数组。
两个爬虫开跑前都会读这个文件：

```python
muted = {m["gid"] for m in board_state.load()["muted"] if m["src"] == "微信"}
if gid in muted:
    continue     # 连表都不查
```

微信侧是"进循环就跳过"，QQ 侧是从 `get_group_list` 的结果里直接剔掉 ——
一个群被退订后，既不会出现在看板上，也**不会消耗任何抓取开销**。

### 3.5 只喊了 @所有人、正文在别处怎么办

群里把正文和 `@所有人` 拆成两条发，这几乎是普遍习惯，而且**方向是双向的**：

```
正文 → @所有人           先写通知，再补一条把人喊出来（尾巴式，最常见）
10:20  王老师   下周三下午 2 点在 9-321 开教研室会，请准时参加。
10:22  王老师   @所有人

@所有人 → 正文           先喊人，紧接着把正文贴出来（同一人）
10:22  李老师   @所有人
10:22  李老师   明天上午 9 点交材料，截止到今天下班。
```

我们按 `@所有人` 命中，抓到的就是那一行 —— 三个字，什么信息都没有。
本机 457 条命中里，这种纯喊话有 **70 条（15%）**。原来的流程在三个地方各丢一次：

| 位置 | 原来的处理 | 后果 |
|---|---|---|
| `wx_crawl.scan()` | `if not strip_keywords(text): dropped_empty` | 微信侧直接 discard |
| `report.collect()` | `if len(text) < 4: continue` | 即使抓到了也进不了看板 |
| QQ 卡片 | 只有 `「@所有人」` 一行 | 看不出是什么事 |

所以通知不是"没抓到"，是**抓到了又被扔掉**。

**结构上的原因**：两条链路都只保留命中行。微信的 SQL 里写死 `LIKE '%@所有人%'`，
压根没有邻居；QQ 侧其实已经把整页 100 条都拿在内存里了，只是过滤完就扔 ——
上下文是白丢的。

**现在的做法**（`app/ctx.py`，两条通道共用）：命中行正文为空时，
**往前看一条、也往后看同一个人补的那条，都有就合并**（`resolve()`）。

但两个方向的可信度来源完全不同，所以判据也不同：

| 方向 | 谁来接 | 判据 |
|---|---|---|
| 往前 | 谁发的都可能 | 靠"像不像通知"，先过闸门再打分 |
| 往后 | **只认同一个人** | 别人插话不算；闸门可放宽，但不能没有 |

往前之所以不能无脑取上一条，是因为真实数据里这些情况混在一起：

```
同一人 2 分钟前发通知，再 @所有人        → 要
别人发的通知，另一个人 @所有人 催一下     → 要（"上面几条是……"）
上一条是闲聊 / 隔了 141 分钟 / 压根没有   → 挂了就是脏数据
```

所以往前分两步，**先过闸门、再打分**：

1. **闸门** `_notice_like()`：不像通知的一分不给。判据是含时间锚点
   （今天/明天/周X/`\d+月\d+日`/`\d+:\d{2}`）、或命中 ≥2 个通知词、或以 `【` 开头。
   另外加一条：没有「请/务必/截止/通知」等强标记的**疑问句**直接出局 ——
   「周三谁有监考」会被日期骗过闸门，但它显然是聊天。
2. **打分**：同一人 +3（最典型）、5 分钟内 +2、含日期 +2、正文 ≥40 字 +1，`≥3` 才采用。

往后这侧更简单：同一个人刚喊完人、紧接着补的那条基本就是正文，取**第一条**即可。
但闸门不能全撤 —— 实测不设限制会把「下午不在这」「@胡微 好的，我修改一下」
这类聊天当成正文。采用条件是二者之一：**看着像通知**，或**成句的长消息（≥12 字）
且不是在对别人说话（不以 `@` 开头）**。

三条经验规则：

- **同一个人发的容忍更久**（往前 30 分钟），别人发的只给 10 分钟。
  "先写正文、忙完再补一条 @所有人"经常拖十几分钟，而别人发的通知通常就在眼前。
- **一段正文只能解释一条喊话**。否则同一则通知会被挂到好几条喊话下面，
  看起来像发了好几遍。用 `used` 集合把用过的候选记下来（前后两侧共享）。
- **合并去重**：上下都命中时按时间顺序拼起来（`\n` 分隔），
  如果一条是另一条的子串就只留更全的那条，总长截到 480 字。

还有一个坑：微信取邻居**必须按 `sort_seq`，不能按 `local_id`**。
微信回填历史时是"老的先入库、新的后入库"的反向插入，`local_id` 几乎是完全倒序的
（实测一个表 23 行里有 22 个逆序点），照 `local_id` 取会取到**更晚**的消息 ——
第一版就是这么写的，覆盖率高得离谱而且全是错的。

**落库形状**：命中行本身就带上了补全结果，看板不用再做判断。

```json
{"time": "2026-10-17 10:22", "sender": "王老师", "text": "@所有人",
 "ctx": "咱们班有同学落下了没在群，看看家长在群的接龙", "ctx_from": "同一人 · 1 分钟前"}
```

多段合并时 `ctx` 里带换行，`ctx_from` 写「同一人 · 前后各一条」。

看板上显示成正文 + 一行浅色来源（`↑ 这条只发了 @所有人，正文取自上下文 · 同一人 · 1 分钟前`），
让人一眼看出这段字**不是原消息里的**。截止时间也从 `ctx` 里提，否则这类通知永远进不了
「即将截止」。

**找不到正文的不硬凑**：仍然收进数据、但看板隐藏，并在页头报数
（"N 条只喊了 @所有人、上下文也找不到正文，已隐藏"）—— 不静默吞掉，也不拿闲聊硬顶。

**效果**：全量 70 条纯喊话补回 16 条（22%），其中 2 条是前后合并。
漏掉的 54 条里 29 条上文是闲聊、17 条间隔过久 —— 这些本来就该弃掉。

## 四、性能实测

| 环节 | 耗时 |
|---|---|
| 微信取密钥（仅首次/失效时） | ~12 s（24 库） |
| 微信解密（每次都要，才能看到新消息） | ~7 s |

所以定时任务里微信那一路几乎无感，QQ 那一路才是主要开销。

## 五、启动与退出

### 5.1 为什么那个黑窗口会自己关掉

最早的做法是 `launch.py` 直接把 `serve_board.main()` 跑在自己的进程里 ——
于是"窗口"就是"服务"，用户手一滑点掉 ×，看板就没了。

现在拆成两个角色：`launch.py` 是**启动器**，`serve_board.py` 是**服务**。
启动器用 `subprocess.Popen(..., creationflags=DETACHED_PROCESS)` 把服务甩到后台，
等服务真的能应答 `/api/health` 才打印一行「就绪」然后退出，窗口随之关闭。

- 关掉窗口（或整个 cmd）不影响服务，因为两边已经没有父子依赖
- 但它**会等**：服务真起来了才退出。起不来就把日志尾巴打出来并 `return 1`，
  `.cmd` 里的 `if errorlevel 1 pause` 会把窗口停住 —— 错误反而更显眼了

### 5.2 为什么探活要先问 socket

`urllib` 探测 `http://127.0.0.1:<port>/api/health` 有个坑：**它会读系统代理**。
用户开着 Clash / 公司代理时，连本机 127.0.0.1 的请求会被丢给代理，
空闲端口只能等到超时 —— 实测扫 10 个端口要 15 秒，启动器看起来像卡死。

所以两件事一起做：

1. 探测本机用 `build_opener(ProxyHandler({}))`，明确绕开代理
2. 先用 `socket.connect_ex` 问"有没有人在监听"（活着 3 ms，死的立刻返回），
   确认有人监听才发 HTTP。某些机器上连空闲端口不回 RST 而是干等，这一步能省掉全部等待

端口本身也不靠猜：服务绑定成功后把实际端口写进 `data/board.port`，退出时删掉。
启动器先读它，再试配置端口，最后才扫 4 个兜底 —— 这也顺便实现了"双击第二次不再起副本"。

### 5.3 停止为什么要单独做一个按钮

服务在后台，窗口又没了，用户没有"关掉"的入口，只能去任务管理器杀 `python.exe` —— 不可接受。
所以页面最下方留了一个"停止看板服务"，POST `/api/quit`，服务端在独立线程里
调 `shutdown()`（不能在请求线程里等自己收尾，会卡死）。

顺带一个坑：没有控制台时 `sys.stdout` 是 `None`，`print()` 会抛 `AttributeError`
把启动器直接打死。任务计划、`pythonw`、被别的进程拉起时都会这样，
所以 `launch.py` 里所有输出都包了一层 try。

### 5.4 更新心跳：为什么比提交 SHA 而不是版本号

"有新版本了"这件事，最直觉的做法是比 `version.py` 里的号。但这里放弃了：

| 做法 | 问题 |
|---|---|
| 比版本号 | 解压版用户手里没有 tag；`version.py` 靠人肉维护，我忘改一次就永远提示有更新 |
| 比发布日期 | 时区、时钟不准、用户改过系统时间，都会误判 |
| **比提交 SHA** | 本地 `git rev-parse HEAD` 一读就有；解压版第一次以远端为基线，之后每次更新成功才推进 |

所以 `update_check.py` 拿 `GET /repos/{repo}/commits?per_page=30`，取最新的 SHA 和
本地的 `installed_sha` 对账：

```
installed_sha 在返回列表里的第 idx 条 → 有更新时 notes = commits[:idx]
找不到（本地太旧，或压根不是这条线）   → 整批 30 条都算新的
```

`notes` 就是提交说明的第一行 —— 它天然是"更新内容"，而且不需要另外维护 CHANGELOG。

**一天只联网一次**，靠 `data/updates.json` 里的 `checked_at` 卡住；心跳线程每 30 分钟
醒一次问"到点没"，到点才真的发请求。失败不重试得那么快：把 `checked_at` 往回拨到
`now - hours + 1h`，一小时后才允许再问 —— 否则会把 GitHub 无认证的
60 次/小时配额白白撞光。

**三种更新方式，按能力降级**：

```
有 .git 且能找到 git   → git pull --ff-only        只传增量，最干净
git 拉不动             → 整包下载覆盖              公共仓库只要读权限
没有 .git              → 整包下载覆盖
```

中间那条是踩出来的：用户克隆时用了 SSH（`git@github.com:...`），换台机器没配 key，
或者公司网络封了 22 端口，`git pull` 直接 `Host key verification failed`。
这时候**不该把用户卡死**，公共仓库整包下载（`codeload.github.com/.../zip/refs/heads/main`）
不需要任何凭据，覆盖一遍效果一样。

但有一种情况**不降级**：git 报 `local changes would be overwritten`。
那说明用户自己改过程序文件，整包覆盖会把他的改动抹掉 —— 宁可失败并让他自己处理。

**覆盖时永远不碰这些**：

```python
SKIP_DIRS = {"data", "napcat", ".git", "__pycache__", "decrypted", "logs"}
KEEP_FILES = {"config.json", "小贾AI群看板.html", "all_keys.json"}
```

`decrypted/` 里是解密后的明文聊天记录，`all_keys.json` 是密钥，`config.json` 是用户的
QQ 号和路径 —— 这些都不在仓库里，但覆盖逻辑必须主动躲开，不能指望"包里没有就不会动"。

**为什么更完必须重启**：`.py` 换掉了，但进程里跑的还是 30 分钟前 import 进来的旧模块。
`POST /api/restart` 会先 `shutdown()` + `server_close()` 把端口真正放开，等 1 秒，
再 `Popen(serve_board.py <同一个端口> --no-open)` 起个新的。新进程用同一个端口，
页面这边轮询 `/api/health` 一通就 `location.reload()`，用户看到的就是"闪了一下"。

这里有个细节：重启中的那个进程，`main()` 的 `finally` 不能再 `unlink` 端口文件 ——
新进程已经写过了，删掉的话启动器就找不到端口。所以有个 `_RESTARTING` 全局标志挡一下。

还有一个更隐蔽的：**这个重启线程必须是 `daemon=False`**。第一版写成了守护线程，
表现是 `POST /api/restart` 返回 `{"ok":true}`、旧进程干净退出、然后……什么都没有。
原因是 `shutdown()` 一返回，`serve_forever()` 就结束，`main()` 跑到结尾，解释器随即开始收尾，
把还停在 `time.sleep(1.0)` 的守护线程直接掐死 —— 起新进程那半句根本没机会执行。
换成非守护线程后，解释器会等它把 `Popen` 做完再退出，实测 4 秒后同端口回到 `{"ok":true}`。

### 5.5 数据源面板：默认选好，改了就记住

看板右上角「数据源」把三件事收到一个面板里：**读不读**（开关）、**从哪读**（QQ.exe / `db_storage`）、
**读谁**（QQ 号 / 微信号）。

**第一版做错了，值得记下来。** 最初的想法是：多账号时**故意留空**，逼用户自己选 ——
理由是"自动选错会抓出一片空，宁可让他麻烦一次"。实际用下来反了：

- 每次打开面板都是空的，看起来像**上次的选择被丢了**
- 想让它不再空，就得再点一次保存，否则每天都会被问一遍
- 用户真正的抱怨变成"这东西记不住事"，而不是"选错了"

现在的做法是**默认选好 + 一改就存**：

```
这台机器上有 2 个微信账号，已按最近使用预选 wxid_g5zui... —— 不对就在下面换
```

默认值的取法：`config` 里存过的 > 自动探测到的第一个（官方 ini 根 + mtime 最新）。
前端 `srcRender()` 直接把 `d.wechat.default` 塞进 `<select>`，所以打开就是选中状态，
不会出现"空着等你选"的画面。

**改了立刻落盘**：`<select>` 的 `change` 和两个开关都直接调 `srcSave(true)`（quiet 模式，
只给一句「已记住」）。只有手动粘路径那种需要输入的，才走「保存」按钮 ——
输入框边打边存容易把半截路径写进配置。

**同一个号的两份副本不算两个账号。** 换过盘的人，`%USERPROFILE%\xwechat_files` 里
往往还留着换盘前的旧目录。只在"官方 ini 有结果"时才优先用官方根（`_wx_data_root()`），
再按 `account`（`wxid_xxx`）去重，官方位置优先、其次取 mtime 新的 —— 否则用户会被问一句
莫名其妙的话，然后随便点一个，把旧副本选上。

**QQ 侧同理，但门槛不同。** `qq_uins()` 扫的是 `napcat/config/napcat_<uin>.json` ——
只有**真登录过的号**才会留下这个文件，比扫注册表靠谱；按文件 mtime 倒序排，
所以"默认选中的那个"就是最近登录过的。`qq_exes()` 要多过滤一层：
注册表 `DisplayIcon` 经常指向 `Uninstall.exe`，按文件名只留 `qq.exe`。

**保存不等于抓取。** 面板只写 `config.json`，不触发一次抓取。这是故意的：
用户可能连着改好几次设置（先换号、再换路径），每次都跑一遍抓取既慢又白费 QQ 的调用次数。
`settings.save()` 走"读盘原文 → 合并 → 临时文件 → `os.replace`"，中途断电也不会把配置写坏，
且只动传进来的那几个键，`paths`、`board` 这些原样保留。

开关最终是被 `launch.py` 的 `cmd_update()` 消费的：

```python
if settings.get("wechat", "enabled", True): ...改成 subprocess 跑 update_wx.py
if settings.get("qq", "enabled", True):     ...子进程跑 auto.py --start
```

也就是说关掉 QQ 之后，**NapCat 根本不会被启动**，不是"抓完再丢掉"。这一点在号被限制过、
想临时只用微信的时候很关键。

### 5.6 视觉：一套变量撑两个主题

看板整块 CSS 只有一个色源 —— `:root` 里的十九个变量（`--bg/-bg2/-bg3/-bg4`、`--line/--line2`、
`--tx/--tx2/--tx3`、`--brand/--brand2`、`--hot/--warn/--ok`、`--qq/--wx`、`--glass/--shadow`）。
浅色主题不是另写一套样式，而是 `:root[data-theme=light]` 覆盖这几个值。**全部规则里没有一处硬编码颜色**，
换主题不需要碰任何一条选择器 —— 这一点用脚本核过：HTML 与 JS 里 `var(--x)` 引用的变量名，
和 `:root` 定义的集合完全一致（19 对 19），没有悬空引用。

**首屏不能闪。** 主题存在 `qad_prefs_v1` 里，如果等业务脚本（在 `</body>` 前）读完再设 `data-theme`，
深色用户会先看到一帧白底。所以 `<head>` 里放了一段同步内联脚本，在 `<style>` **之前**
把属性定好 —— 它只读 `localStorage` 和 cookie，不依赖任何库，出错就静默走默认深色。

**顶栏故意不吸顶。** 改版时试过 `position:sticky`，玻璃拟态配 `backdrop-filter` 很好看，
但这个顶栏含品牌区 + 四个数字卡 + 一整条筛选栏，撑到 190px 左右；一吸顶就吃掉五分之一屏幕，
往下翻消息反而更难用。旧版也没吸顶，这里保持原样 —— 观感让步给可用性。

**数字卡当开关用。** 顶上四个数字里，"14 天内到期"和"已完成"是可点的：
点前者等于勾上「只看带截止时间的」，点后者等于切换「隐藏已完成」。
它和下面的勾选框操作的是**同一个 `checked` 状态**，所以两边永远同步，不存在两套逻辑打架。
`render()` 顺带把"已完成 · 已收起 / 显示中"写进标签，用户不用去猜现在是什么状态。

**动效要能被关掉。** 卡片入场用 `@keyframes rise`，但整份样式末尾有一条
`@media(prefers-reduced-motion:reduce){*{animation:none!important;transition:none!important}}` ——
系统开了"减少动态效果"就全停，不做"我们觉得好看就行"的决定。

### 5.7 「近 N 天」的 N 是能改的，而且必须走服务端

标题下面原来那一行是：

```
抓取时间 2026-10-30 19:41 ｜ 只显示最近 30 天的、未过期的 ｜ 38 条已标记完成，18 条已过期，4 条……，已隐藏
```

三件事挤一行，其中两件没人看。现在缩成 `抓取 2026-10-30 19:41 · 近 30 天`，
那个 `30` 是个**看起来像文字的数字框**（`border` 透明，hover/聚焦才显出输入框），
改完回车就打 `POST /api/days`，存进 `config.json` 的 `days`，然后整页重取。

**为什么不能在浏览器里过滤。** 这是最容易走错的一步：`DATA` 里只有已经筛过的行，
想「多看几天」的话，那几天的数据**服务端根本没发下来**，前端再聪明也变不出来。
反过来「少看几天」倒是能前端过滤，但那样就出现两套口径 —— 于是统一让服务端重算：
`days` 只存一处（`config.json`），页面每次都是 `report.build(today, settings.days())` 的产物。

**几个刻意的边界**：数字框 `min=1 max=365`，JS 里也夹一次（`abc` → 1，`999` → 365），
因为 `type=number` 在浏览器里能被各种方式绕过去；值没变就不发请求；
直接双击 `看板.html` 打开时禁用并写明原因（没有服务可改），「看示例」模式下同样禁用 ——
否则示例里随手一改，会把你的真实配置写掉。

被隐藏的明细没删掉，挪进了那个数字框的 `title`：悬停才出现，想看的人在，不想看的人眼前干净。
