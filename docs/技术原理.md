# 技术原理

这份文档记录两件事：**数据是怎么拿到的**，以及**为什么这么拿不会把号跑封**。
踩过的坑都写在里面，省得你再踩一遍。

> 文中提到的文件位置：代码都在 `app/`，运行时产物都在 `data/`
> （`data/群公告_*.json`、`data/微信群公告_*.json`、`data/board_state.json`、`data/data_store.json`、`data/logs/`），
> 解密产物在 `app/vendor/wcdb-key-tool/decrypted/`。

---

## 一、QQ 侧

### 1.1 为什么要"抓完就跑"

NapCat 的工作方式是把自己作为一个 Node 插件**注入到 QQ 进程里**，然后对外暴露一个
OneBot 协议端点。问题在于注入时机：它只能挂到**新创建**的 QQ 进程上。

如果你的 QQ 已经开着，`auto.py` 是注不进去的 —— 这不是 bug，是机制决定的。
所以整个流程被设计成：

```
检测 QQ 是否已开
  ├─ 已开  → 直接放弃 QQ 这条路（不硬来，不杀你的进程）
  └─ 没开  → 用 NapCat 的快速登录拉起 QQ
              ↓
        等 OneBot 端点就绪（反向 WS 连上来）
              ↓
        get_group_list → 逐群 get_group_msg_history，只读
              ↓
        抓完 → 立刻退出这个 QQ 进程
```

退出这一步很重要：跑完之后机器的状态回到"你平时手动登录 QQ"的样子，
不会留下一个常驻的、被动过手脚的客户端。

**关于扫码**：拉起 QQ 的命令是 `NapCatWinBootMain.exe QQ.exe <inject.dll> -q <QQ号>`，
`-q` 就是快速登录 —— 它不重新走一遍密码/扫码流程，而是复用本机已有的登录态
（NapCat 首次登录成功后会写一份 `config/napcat_<QQ号>.json`，有这个文件基本就代表登录态还在）。

所以：

- 登录态有效 → 静默拉起，**不用扫码**
- 登录态失效 / 首次 / 换号 → QQ 会要求登录，**扫一次**，之后长期免扫

`crawl_ws.py` 侧给 NapCat 的连接等待上限是 **120 秒**，加上拉起后的 8 秒固定等待，
实际留给人扫码的窗口约两分钟。超时会打印「等了 120 秒 NapCat 仍未连接」，
并且 `auto.py` 会把这次拉起的 QQ 整棵树收掉，不留残留。

### 1.2 消息怎么取

`crawl_ws.py` 起一个本地 WebSocket server，NapCat 反向连过来（所以不需要向任何端口发请求，
也绕开了 3000 端口被系统保留的问题）。

一次完整的抓取：

1. `get_group_list` —— 拿群列表，先剔掉已退订的群（`board_state.json` 里的 `muted`）
2. 对每个群 `get_group_msg_history`，每页 100 条
3. 只认 `message[].type == "at"` 里 `qq` 为 `all` 的消息 —— 也就是 `@所有人`
4. **增量策略**：新消息在前，一旦翻到比上次记录更旧的消息就停，不再往下翻
5. 结果合并进累计库 `data_store.json`，按 `群名` 分组

首次运行（没有累计库）或加 `--full` 时才回溯完整时间窗口。

### 1.3 缓存与幂等

`data_store.json` 是滚动累计的，按 `(time, sender, text)` 去重。
重跑不会产生重复条目，也不会丢历史 —— 这让"每天跑一次"变得安全，
哪怕某天因为 QQ 已开着跳过了一次，第二天照样补齐。

## 二、微信侧

这是整个项目技术含量最高的部分，也是最容易被想歪的部分。

### 2.1 数据在哪

微信 4.x 的数据目录长这样（真实路径由 `%APPDATA%\Tencent\xwechat\config\*.ini`
里的那行字符串指定，可以整个挪到别的盘）：

```
xwechat_files/
└─ wxid_xxxxxxxx_1234/
   └─ db_storage/
      ├─ contact/contact.db        联系人、群名、备注
      ├─ message/message_0.db      消息，按会话分表
      ├─ message/message_1.db      分片
      ├─ session/session.db        会话列表
      └─ ...
```

**群消息在 `message_N.db` 里，表名是 `Msg_<md5(群ID)>`。** 群 ID 形如 `123456789@chatroom`，
所以你得先算出 md5 才能定位到表 —— 这是第一个坑。

行结构的关键字段：

| 字段 | 含义 |
|---|---|
| `local_type` | `1` = 文本；其他是图片/语音/引用等 |
| `message_content` | 文本内容，`"wxid_发送者:\n正文"` |
| `WCDB_CT_message_content` | 压缩标记，`4` 表示这列是 zstd 压缩的（文本不走） |
| `real_sender_id` | 指向 `Name2Id` 表的 rowid，用来还原发送者 |
| `create_time` | Unix 秒 |

所以取一条 `@所有人` 的流程是：`Msg_<md5>` 表 → 过滤 `local_type=1` →
`message_content LIKE '%@所有人%'` → 按 `real_sender_id` 关联 `Name2Id` 拿 wxid →
再拿 wxid 去 `contact` 表查 `remark` / `nick_name` 显示名。

### 2.2 库是加密的（SQLCipher 4）

`db_storage` 下的 `.db` 全是 SQLCipher 4 加密的：

- 算法：AES-256-CBC + HMAC-SHA512
- 页大小 `4096`，每页尾部保留 `80` 字节 = `IV(16) + HMAC(64)`
- 第 1 页结构：`[salt 16][密文 4000][IV 16][HMAC 64]`
- 每个库的 salt 独立，所以**每库一把独立派生密钥**

HMAC 校验时页码是**小端序**（`struct.pack('<I', 1)`）—— 这是第二个坑，
按大端写会全部校验失败。

### 2.3 为什么老工具在微信 4.1+ 全部失效

以前大家都是"扫进程内存找 `x'<64位十六进制key><32位salt>'`"这个模式。
微信 4.1.10 之后这条路被彻底堵死：

> 进程内存里不再缓存算好的明文密钥，只剩一个 passphrase。
> 真正的密钥要用 PBKDF2-HMAC-SHA512、**256000 轮**现算现用，算完就丢。

所以扫描 2GB 内存得到 **0 命中** 不是工具写错了，是设计上就没有了。
这也是为什么这个项目直接 vendor 了
[wcdb-key-tool](https://github.com/TANGandXUE/wcdb-key-tool) 而不是自己硬写。

### 2.4 现在的取密钥方式

思路是"不猜，跟着微信自己的代码走"：

```
在内存里找 com.Tencent.WCDB.Config.Cipher 这个字符串字面量（锚点）
  → 顺着引用找到持有它的对象
  → 读出那段结构，用固定 27 字节掩码 XOR 还原
  → 从还原结果里读出 x'<passphrase><salt>'
  → PBKDF2-HMAC-SHA512(passphrase, salt, 256000) 派生 32 字节密钥
  → 用第 1 页的 HMAC 验证（对得上才认）
```

实测：24 个库 / 12 秒 / 24 个全部通过 HMAC 校验。

**安全边界**，逐条说明：

- 只用 `OpenProcess(PROCESS_VM_READ)` + `ReadProcessMemory`，**只读**
- 不 `WriteProcessMemory`，不 `CreateRemoteThread`，不注入 DLL，不挂调试器
- 不改微信安装目录、不改配置、不动登录态
- 不联网，一个包都不发

换句话说，它做的事和你用 Process Explorer 看一眼微信内存没有本质区别，
只是它看得更准、并且能算。

### 2.5 解密与查询

拿到密钥后：

```python
# 每页解密后，把尾部 80 字节替换成 0，其余保留
# 第 1 页特殊：把 [salt 16] 换回 "SQLite format 3\0"
plain = aes256cbc_decrypt(key, page[:4096-80])
```

产物写到 `decrypted/`，是**可以直接用 sqlite3 打开**的普通数据库。
之后所有查询都是标准 SQL，跟加密无关了。

解密只读原库，不动 `db_storage` 里的任何文件。

### 2.6 为什么微信不用退出

因为整个链路是 **磁盘 → 解密 → 查询**，全程不需要微信配合。
微信在跑的时候文件会有 WAL 尾巴，但主库本身是一致的，读出来最多差最后几条，
下次跑自然补上。

这一点和 QQ 形成了鲜明对比：QQ 的数据在游戏进程的内存里，微信的数据在文件里。
所以一个必须"抓完即退"，一个可以永久常驻。

## 三、跨通道设计

### 3.1 统一的数据形状

两个通道最终写出**同一种结构**的 JSON，所以下游只有一套代码：

```json
{
  "群名 (群ID)": [
    { "time": "2026-10-29 09:12", "sender": "辅导员-王老师", "text": "@所有人 请于…" }
  ]
}
```

- QQ → `群公告_<日期>.json`
- 微信 → `微信群公告_<日期>.json`

`report.py` 读它们，给每行打上 `src` 标签（`QQ` / `微信`），然后按 `src` 分成两列渲染。

### 3.2 稳定 ID：为什么"已完成"会莫名其妙失效

看板用一条哈希当每行的 ID：

```
sha1(src | gid | time | sender | text[:40])[:12]
```

**只取不会随重跑变化的字段**。这里有个血泪教训：早期版本把 `topic`（自动生成的话题归类）
也算进了种子里，结果每次重跑规则微调一下话题，所有 ID 全变，用户之前点的"已完成"就
集体失联 —— 表现就是"标记完成后刷新又出现了"。

同理，`days` 窗口、过期判断这些也不能进种子。

### 3.3 状态为什么不能只放 localStorage

`present_files` 之类的预览面板，每次给你的是一个
`http://127.0.0.1:<随机端口>/static-html/<hash>/` 地址。
**端口变了，origin 就变了，localStorage 就是另一个世界。** 于是"点了完成、刷新又回来了"。

所以状态走三层：

1. 看板服务在跑 → POST 到 `/api/state`，写进 `board_state.json`（最可靠）
2. 没有服务 → 写 localStorage **和** cookie（cookie 用 `path=/`，跨端口共享）
3. 读的时候取并集，任一处可用就不会丢

界面上有个小标签实时告诉你当前处于哪一档，
如果是"仅本浏览器有效"，就说明该用 `启动看板.cmd` 了。

### 3.4 退订群为什么要在爬虫侧生效

点 `✕` 不只是界面上 `display:none`，它写进 `board_state.json` 的 `muted` 数组。
两个爬虫开跑前都会读这个文件：

```python
muted = {m["gid"] for m in board_state.load()["muted"] if m["src"] == "微信"}
if gid in muted:
    continue     # 连表都不查
```

微信侧是"进循环就跳过"，QQ 侧是从 `get_group_list` 的结果里直接剔掉 ——
一个群被退订后，既不会出现在看板上，也**不会消耗任何抓取开销**。

## 四、性能实测

| 环节 | 耗时 |
|---|---|
| 微信取密钥（仅首次/失效时） | ~12 s（24 库） |
| 微信解密（每次都要，才能看到新消息） | ~7 s |
| 微信抓取 + 出看板 | ~2 s |
| **微信日常增量合计** | **~6 s**（跳过取密钥） |
| QQ 启动 + 抓取 + 退出 | 40–90 s（大头是 QQ 冷启动） |

所以定时任务里微信那一路几乎无感，QQ 那一路才是主要开销。
